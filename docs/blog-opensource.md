# 让排查自己发生：我把线上问题排查交给了 Columbo

> 源码：[https://github.com/caps-xia/columbo](https://github.com/caps-xia/columbo)｜ 默认账号 `admin / admin123`，clone 下来 5 分钟跑起来
>
> 如果你也在用腾讯云，日志在 CLS（日志服务）里——这个项目就是为你写的：配好密钥，你就得到一个会自己查日志、读代码、翻经验库、写结论报告的排查助手。

## 先说一个大家都在经历的

用户（或者客服转过来）甩来一句话：**"生产环境订单下单失败，帮我看看。"**

接下来你的半小时大概率是这样度过的：打开日志控制台，想检索词，拼查询语句；命中太多，加过滤条件再来一遍；终于找到那条 ERROR，抄下 traceId；再拉全链路，发现下游服务返回了个 `success:false`；切到 IDE，grep 异常类名，找到文件，从 800 行里读出那 80 行；最后在脑子里把因果链拼起来，回一句"这是 XX 配置导致的，改一下就好"。

这套动作里没有任何一步是"难"的，每一步都是检索、阅读、拼接。**它浪费的不是智力，是工程师的时间**——而且是每个月都要重复浪费一遍的时间。更糟的是，上次排查这个问题的记忆只存在于某个人脑子里，那个人休假，问题就得从零再查一次。

所以我写了 Columbo：一个专注做一件事的开源项目——**AI 线上问题排查助手**。它的能力就四样：腾讯云 CLS 日志、本地源码副本、排查知识库（llmwiki）、可选的只读数据库，四样交给一个智能体，它还你一份带置信度的根因报告。

一句话概括它的定位：**把"日志、代码、经验"交给智能体，它还你一份带置信度的根因报告。**

## 一条排查请求的旅程

以"生产环境，订单交易，下单失败，帮我排查下原因"这句话为例，看看它在 Columbo 里会经历什么：

**1. 话术路由。** 用户不会说应用名，只会说"订单、下单"。`resolveRouting` 工具按配置好的词典（环境词 + 业务线词 + 站点职责）把口语解析成结构化候选：CLS 应用名（`myapp.java.order`）、本地工程目录（`order-service`）、代码分支（`master`）。识别不了就把全部候选摆出来让模型向用户确认，不猜。

**2. 查经验库。** 动手之前先 `searchKnowledge` 检索本地知识库——历史排查案例、错误场景词典。命中了就直接复用旧结论（旧案例里的行号会漂移，但类名/报错文案是稳定锚点，会用 `searchCode` 在最新代码里重新确认）。

**3. 探量再查。** 先 `countClsLog` 探量：不拉日志，只拿命中条数和**时间分桶分布**——一眼看出问题集中在哪个时段。命中量很大就先告知用户预估数据量再决定怎么收窄；多应用初筛时一轮并行打包多个探量调用，墙钟取最慢而非求和。

**4. 检索与还原现场。** `queryClsLog` 按 traceId/关键词/级别拉日志（有 traceId 用 contextId 精确追踪全链路）；对关键异常 `queryClsLogContext` 以那条日志为锚点取前后各 10 条，还原故障现场。有个很实用的"两跳追踪法"：第一跳按报错关键词 + ERROR 级定位；第二跳取 ERROR 的 contextId 拉全链路**不带级别过滤**——因为三方接口的响应多是 INFO 级，漏看了会把三方返回 `success:false` 误判成自己的校验问题。

**5. 代码定位。** 异常栈里的 `Foo.java:123` 交给 `searchCode` / `readCodeFile`：本地维护多环境代码副本（各环境分支不同，传错环境会定位到错误代码，工具返回实际读取的分支），按行号读上下文，沿 Controller → Service → DAO 追调用链。

**6. 数据核查（可选）。** 日志说不清"是我方数据错了还是外部系统的问题"时，排查助手会直接用数据库工具核实：看连接 → 查表结构 → 只读 SELECT。工具层只允许 SELECT/SHOW/DESC/EXPLAIN，接的也是只读从库——想用就配一个连接，不想配它就如实写进"未决项"，绝不编造数据。

**7. 产出报告。** 这是最有意思的一步，下面单独讲。

**8. 沉淀速记。** 根因验证闭环**且置信度达"高"档（≥85%）**时，`appendKnowledgeNote` 把本次排查沉淀成结构化速记（现象/环境/排查过程/根因/解决方案/置信度）写进知识库收件箱——**下次同类问题，第 2 步就直接命中了**。门槛是刻意的：错误结论入库污染的是所有后续排查，宁缺毋滥；中低置信度的结论留在报告里，等复核升档再沉淀。

## 两个值得展开的设计决策

### 取证与成文分开：两阶段 Sequential 工作流

排查 agent 的指令有近万字（路由规则、时间换算规则、追踪技巧、五条证据纪律、报告结构……），如果让一个 agent 又查又写，上下文会变成"万字指令 + 全部查询历史 + 报告规则"的叠加，又贵又容易顾此失彼。

Columbo 拆成了两个 agent：

- **取证 agent**：扛全部工具和长上下文，产出一份结构化**取证档案**（环境与路由/问题现象/知识库命中/日志证据/代码证据/根因分析/未决项），档案以一行 `---` 结尾；
- **成文 agent**：**零工具**，只读会话里的档案，按固定结构产出最终报告（结论速览/时间线/根因三问/修复建议分"立即止血+长期修复"/影响范围/**置信度与提升路径**/用户回复话术）。上下文从"万字指令+全部查询历史"缩到"档案+成文规则"。

成文 agent 有一条铁律：**报告只依据档案成文，禁止新增、推测或"自行查证"档案中没有的事实**。档案的【未决项】必须如实进入置信度扣分。这直接治住了 agent 排查最致命的病——**一本正经地编证据**。

（为什么不用 Loop 批判环？因为工具执行全在 MySpringAI 内部循环完成、不进 ADK 会话，`setEscalate` 根本到不了 LoopAgent，只剩 maxIterations 盲转，没有质量闸门可言。自检要求改为并入成文 agent 的输出前清单。仓库里还保留了一个单阶段直出版做 A/B 对比：省掉成文阶段每场约 2 分钟和 1.5~2 万 token，代价是无独立复核。）

### 给弱模型修路，而不是给它设卡

这套系统跑在 flash 档模型上，所以很多设计本质是在**给弱模型修路**：

- **工具结果里直接写"下一步查法"**。命中 1747 条只返回 20 条时，在结果里附上"缩小时间范围或换更精确的关键词重查，勿用相同参数原样重查"——比事后拦截提示更治本（后面踩坑实录会讲这句是怎么来的）。
- **凭证类错误明确说"重试无效"**。token 过期时弱模型会连发三次一模一样的调用直到被熔断，因为错误文案里的"请检查参数后重试"会被它当成重试指令。现在这类错误会附上"该错误为凭证/环境问题，重试或修改参数均无法解决，请勿再次调用本工具"。
- **相对时间服务端换算**。模型不知道今天几号，让它换算"最近 2 小时"会编造日期（实测能差一年）。所以"最近 N 小时"传 `timeWindow`，服务端按真实时钟换算。
- **报告置信度必须给区间和提升路径**。高=85~95%、中=50~80%、低=20~45%，禁止超 95%、禁止虚假的个位精度，末尾必须写"还缺什么能升档"——低置信度时措辞强制用"疑似/可能/待验证"。

## 踩坑实录（每一条都有线上事故编号）

1. **模型循环重发相同调用。** 某天线上：命中 1747 条返回 1 条，弱模型读到"命中很多"后原样重发同一调用，直到循环熔断。修法就是上面的 suggestion 字段——在工具结果里告诉它下一步怎么查。
2. **token 过期连打三轮。** 同一毫秒两条相同查询、连续 3 轮完全相同的调用，全被熔断器拦下。修法是凭证错误识别 + "重试无效"处置语，以及并行批次里的重复调用去重（同参调用只执行一次，结果按各自 toolCallId 复制回填）。
3. **正则回溯打满线程。** 模型生成的正则在长行上回溯，一个 `searchCode` 把线程占死。换 RE2（线性时间引擎），彻底杜绝 ReDoS。
4. **413 上下文超长。** 长会话撞网关上限，本轮产出全丢。修法是"紧急压缩重试"：压缩旧会话 → 翻篇结转摘要 → 重放本条消息；已产出内容后撞超长则保留阶段性结果，用户发"继续"由翻篇机制接手。
5. **SSE 断开空烧。** 用户关掉页面，LLM 订阅还在跑。现在断开即取消订阅。
6. **证据纪律的三次误判。** podName 哈希并存被当成"连续发布未下线"（实际当天无发布）；下游 NPE 失败重投被当成"多实例重复消费"；一个字典标识字段被当成"三方推送订单"。三条都沉淀进了取证的【证据纪律】：间接迹象不得进根因链；效应≠原因；字段语义以代码为准（读枚举定义和全部写入点再下结论）。
7. **截图是强锚点。** 用户贴报错截图后，多模态模型提取的不只是报错文案，还有时间戳——页面时间是用户操作发生时间，查日志以它为中心取 ±10 分钟窗口，命中率远高于盲扫。

## llmwiki：让排查经验复利

排查助手最容易被忽视的一环是**经验沉淀**。Columbo 内置了一个本地知识库（我叫它 llmwiki）：

- 每次根因验证闭环后，`appendKnowledgeNote` 自动把本次排查沉淀成结构化速记（现象/环境/排查过程/根因/解决方案/置信度），写进知识库收件箱，由库内的分拣规则归档；
- 下次同类问题，排查流程第 0 步 `searchKnowledge` 直接命中——旧案例的行号会漂移，但类名/报错文案是稳定锚点，会在最新代码里重新确认；
- 前端带知识库浏览页，支持目录树、全文搜索、frontmatter 元数据（标签/系统/日期）；
- 检索是关键词+向量 RRF 融合的混合检索（未配 Embeddings 服务时自动熔断为纯关键词，不阻塞）。

**你的团队排查一个问题的成本，应该随排查次数下降**——llmwiki 就是冲这个去的。仓库里带了一个开箱示例库（`docs/llmwiki-template/`：分拣规矩 + 示例速记 + Pattern 页），以及一份**每日分拣提示词**——每天丢给你的 AI 助手跑一次，收件箱就永远干净：查重归档、脱敏红线复查、置信度二次门槛（中低置信度进"待复核"区，复核升档才入正式库）、套路提炼、索引同步，全自动。

## 可选的数据库排查：接一个只读从库就能用

很多"日志查到了但差一步确认"的场景（配置值到底是多少、状态字段的当前值），需要查一眼库。Columbo 把数据库查询做成**可选能力**：默认不装配；放开一行 yml 导入，配一个**只读从库/只读账号**连接（密码环境变量注入），就多一个数据库查询助手——表结构 → 写 SQL → 解读一条龙，工具层只允许 SELECT/SHOW/DESC/EXPLAIN，任何写操作直接拒绝。用户侧的接入成本就是"要一个只读连接"，不需要动生产库权限。

工程本体是 DDD 六模块（types/api/domain/infrastructure/trigger/app，COLA 映射与 ArchUnit 分层守护见 `docs/architecture-cola.md`）：Sa-Token 登录鉴权、H2/MySQL 会话持久化（默认零依赖 H2 文件库）、思考过程流式捕获、上下文自动翻篇+小模型压缩、模型池运行时热切换、多厂商供应商注册表、traceId 全链路日志。新增一个智能体 = 一份 yml；新增一个工具 = 一个 `@Tool` 类。

三步跑起来：

```sh
# 1. 配密钥
export LLM_API_KEY=sk-xxx                      # 默认智谱开放平台，任何 OpenAI 兼容网关都能换
export TENCENT_CLOUD_SECRET_ID=AKIDxxx         # 腾讯云子账号，建议只授 QcloudCLSReadOnlyAccess
export TENCENT_CLOUD_SECRET_KEY=xxx

# 2. 启动（JDK 17）
mvn -pl columbo-app spring-boot:run

# 3. 打开工作台
open http://localhost:8080/app/                # admin / admin123
```

想开数据库排查：放开 `spring.config.import` 里的 `agent/db-query.yml`，配一个只读从库连接即可；不想开就当它不存在。

CLS 配置只需在 `application-dev.yml` 的 `troubleshoot.cls` 里填日志集 ID（或启动后 `POST /api/v1/cls_topics_sync` 自动同步全部主题）；把你的工程 clone 到 `./code`，代码侧证据也就绪了。**换句话说：日志在腾讯云 CLS 里的团队，当天就能用上。**

## 写在最后

我不鼓吹"AI 替代工程师排查问题"——置信度 95% 的报告也需要人来签字。Columbo 的朴素定位是：**把排查的第一个小时交给它**。检索、翻页、读代码、拼时间线这些机械动作它来做；你从"结论速览"进，直接校验证据链、做决策。而每一次人工确认后的速记沉淀，都在让下一次更快。

项目全程只读不写（不改文件、不执行写操作、数据修复只给建议方向），密钥全部环境变量注入、最小权限（CLS 只读、DB 只读账号）——把智能体放进生产环境该有的谨慎，都在代码里了。

如果它帮你省下了一个小时，欢迎来 [github.com/caps-xia/columbo](https://github.com/caps-xia/columbo) 点个 Star，也欢迎提 issue 交流你的排查场景。
